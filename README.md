# CodeAtlas

CodeAtlas is a system for creating and maintaining a structured, reversible description of a codebase. It serves as a two-way bridge between human intent and source code, designed to be driven by Large Language Models (LLMs) in a cost-effective, human-in-the-loop workflow.

The core idea is to treat code and its structured specification as two sides of the same coin, enabling two inverse operations:

1.  **Summarization (Code → Spec):** Automatically analyzing source code to produce a token-efficient JSON "atlas" that describes the entire project structure, down to the class and function level.
2.  **Implementation (Spec → Code):** Using a structured JSON "change packet" (generated by an LLM from the atlas) to automatically modify the code.

This approach dramatically reduces the number of tokens required for an LLM to understand a codebase and provides a safe, automatable way to apply changes.

## Core Workflow

The primary workflow is designed to be manual by default to avoid unexpected costs, with optional flags for direct LLM API integration.

1.  **`atlas plan`**: A developer specifies a change they want to make (e.g., "add a parameter to function `foo` in `bar.py`"). The tool generates a detailed, copy-paste-ready prompt containing the project's structured description and the user's request.
2.  **Human-in-the-Loop**: The user copies this prompt and pastes it into an LLM of their choice (e.g., a web UI like ChatGPT or Gemini).
3.  **LLM Generates Change Packet**: The LLM processes the prompt and returns a structured JSON object—the "change packet"—that describes the exact code modifications required.
4.  **`atlas apply`**: The user saves this JSON to a file and runs the `apply` command. The tool validates the packet and executes the changes, automatically modifying the source code.

This project provides the engine for this workflow, acting as the bridge between the developer, the LLM, and the repository.

## Stateless by Design: Resilience to Interruption

A core design principle of CodeAtlas is that the LLM is treated as a stateless function call. It does not need to maintain any memory or history of the project.

This is achieved by making every interaction self-contained:

1.  **Local State:** All project state and history are stored locally in your repository and the `.atlas` directory.
2.  **Self-Contained Prompts:** The `atlas plan` command generates a prompt that includes all the necessary context for a single, specific task.
3.  **Persistent Changes:** The `atlas apply` command commits the results of the LLM's work directly to the filesystem.

This ensures that if the process is interrupted at any point—whether due to a network issue or a day-long break—no context is lost. The next time you run a command, it will simply pick up from the current, saved state of the project, preventing repeated work and ensuring a resilient and predictable workflow.
